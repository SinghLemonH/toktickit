## 2. My Reflection

Working with an AI coding partner using Spec-Driven Development (Spec DD) and Test-Driven Development (TDD) across Lab 3 fundamentally elevated both development velocity and software engineering discipline. In a complex, multi-role ticketing application with strict state machines and dual-channel communication, casual conversational prompting quickly leads to security lapses and regression bugs. By shifting to a **Senior Prompt Engineering** paradigm: declaring domain invariants, security threat models, and explicit acceptance criteria before any code is generated: the AI served as a high-precision force multiplier rather than a loose generator.

### 2.1. Specification-Agent vs. Coding-Agent Synergy
A defining breakthrough in this sprint was separating the AI into two complementary operational roles:
1. **The Specification Agent**: Deployed during the upfront planning phase (Issue #29) to interrogate project constraints, examine threat vectors, and synthesize formal RFC-style contracts (`specification.md`, `api-spec.md`, `ui-spec.md`, `tests.md`). By requiring the specification agent to produce numbered Functional Requirements (FR-01 to FR-20), Business Rules (BR-01 to BR-17), and Acceptance Criteria (AC-01 to AC-20), we established unambiguous system boundaries before writing a single line of application code.
2. **The Coding Agent**: Deployed during incremental feature branches (Issues #30 through #35) with scoped prompts referencing exact requirement IDs. Because the coding agent operated within pre-validated contracts and automated test assertions, hallucination and architectural drift were reduced to zero. Whenever an implementation question arose, the agent resolved it by consulting the specification rather than making arbitrary assumptions.

### 2.2. Key Architectural Insights & Engineering Discipline
1. **Contract-First Rigor Prevents Scope Creep**: Establishing detailed API and UI specifications upfront eliminated ambiguity between backend route guards and frontend role-based rendering.
2. **Context Continuity Architecture**: Embedding a persistent state tracker inside `AGENTS.md` solved the common failure mode of AI context loss across conversation resets, guaranteeing seamless handoffs between sprints.
3. **Defensive Security by Design**: Directing the AI to incorporate server-side RBAC validation independently of UI controls ensured that "hiding a button is not authorization" remained an uncompromised system invariant.
4. **Backward-Compatible Schema Evolution (Expand-and-Contract)**: Migrating relational models without breaking prior sprint test suites requires disciplined staging. Retaining `DevRequester` during the transition while migrating ticket foreign keys cleanly to `User` and synchronizing sequence IDs ensured 100% regression pass rates across all Lab 1 and Lab 2 automated suites.
5. **Stateful Security with Stateless Ergonomics**: Establishing signed HTTP-only cookies while maintaining an active-user database verification layer combined the security advantages of server-managed sessions with the operational simplicity of cookie tokens. Quarantining accounts flagged with initial passwords at the middleware level prevented unauthorized API access even if client-side route guards were bypassed.
6. **Dual-Channel Integrity and State Machine Separation**: Implementing public comments alongside resolution flags demonstrated the importance of keeping requester intent distinct from administrative state machines. Allowing requesters to signal 'Problem Appears Resolved' with an automated public notice without granting them permission to mutate ticket status to `RESOLVED` preserved operational auditability while respecting role-based state transition invariants.
7. **Permitted State Transitions & Human-in-the-Loop Safeguards**: Implementing BR-15 status transitions reinforced the necessity of defensive state machines. Hardcoding transitions in pure TypeScript (`ALLOWED_STATUS_TRANSITIONS`) and enforcing them at the Express controller level guaranteed that invalid state jumps (such as jumping directly from `NEW` to `CLOSED`) return immediate 400 Bad Request errors, while the frontend guides the user with confirmation dialogs.
8. **System Self-Preservation & Administrative Invariants**: Building the User Management module under Issue #34 highlighted the criticality of business-logic self-preservation. Administrative accounts cannot be permitted to deactivate themselves (BR-16), nor can the system allow deactivating or demoting the last active Administrator (BR-17). Enforcing these invariants via database transactions and clear feedback banners prevents fatal lockout states.

In conclusion, pairing human architectural oversight with AI-assisted Spec DD and TDD created a repeatable, robust engineering workflow. The result is a rock-solid code base with 158 passing automated tests (111 server, 47 client) and zero functional regressions.
